## 상황 1: 스프링 부트 배치 서버의 메모리 압박

### 모범 답안

#### Q1: 왜 8초의 GC pause가 발생했는가?

**근본 원인:**
- `findAll()`로 100만 건을 한 번에 로드 → Young Generation이 순간적으로 포화
- Young GC로 정리할 수 없는 대량의 생존 객체 발생 → Old Generation으로 승격(promotion)
- Old Generation이 차면서 Full GC 발생 (STW: Stop-The-World)

**8초의 의미:**
```
GC Pause Time = 실제 애플리케이션이 정지되는 시간
- 이 시간 동안 모든 사용자 요청 처리가 중단됨
- 배치 작업에선 처리 중단, API 서버라면 응답 지연
- Old Generation 전체를 mark-sweep-compact 하는 동안 발생
```

**JVM이 이 상황을 겪는 과정:**
```
시간순서:
1. 객체 할당 속도 > GC 회수 속도
2. Young Generation (256MB 가정) 포화
3. Young GC 발생 (Minor GC, ~100ms)
4. 100만 건 중 대부분이 생존 (아직 처리 중)
5. 생존 객체 → Old Generation으로 승격
6. Old Generation도 점점 차오름
7. Old Generation 80% 이상 도달
8. Full GC 시작 (CMS/Serial/Parallel)
9. 모든 스레드 정지, 8초 동안 Mark → Sweep → Compact
10. 배치 쓰레드도 정지 → "작업이 느려짐" 보고
```

#### Q2: 100만 건이 어느 영역에 할당되고 언제 버려지는가?

**할당 흐름:**

```
┌─────────────────────────────────────────────────────────┐
│                    JVM Heap (2GB)                        │
├──────────────────────────┬────────────────────────────────┤
│   Young Generation       │    Old Generation             │
│   (약 512MB)             │    (약 1.5GB)                 │
├───────┬───────┬──────────┼────────────────────────────────┤
│ Eden  │ S0    │ S1       │ Tenured                        │
│(256MB)│(128MB)│(128MB)   │                                │
└───────┴───────┴──────────┴────────────────────────────────┘

+ Metaspace (클래스 메타데이터, 별도 native memory)
```

**100만 건 로드 시나리오:**
```
시점별 객체 위치:

[초기] List<Order> orders = findAll(); // 100만 건 요청
→ Order 객체 1000000개 생성
→ 할당 영역: Eden (Young Generation)

[로딩 중] 
500MB 할당 → Eden 채움
→ Young GC 트리거 (GC threshold 도달)
→ 아직 루프 처리 중이므로 모든 객체 생존
→ Survivor Space → Old Generation으로 승격
→ orders 리스트 자체도 Old Generation에 고착

[처리 중] for(Order order : orders) {...}
→ 각 order 처리 시 생기는 임시 객체들은 Eden에 할당
→ 하지만 orders 리스트는 Old Generation에서 계속 참조됨
→ 참조되는 동안 GC 대상 아님 (GC root 경로)

[버려지는 시점]
→ for 루프 끝남 & orders = null; 이후
→ 다음 Full GC 때 수집 가능
→ 하지만 그 전까지 1.5GB Old Generation을 점유
```

#### Q3: 힙 2GB→4GB와 JPA batch size 1000의 차이

**힙을 4GB로 늘리는 경우:**
```
문제 해결? 아니다, 연기할 뿐이다.

New Heap Size (4GB):
- Young: 1GB, Old: 3GB
- 처음엔 이전보다 GC가 덜 자주 일어남
- 하지만 Old Generation이 더 크므로
- Full GC가 일어나면 mark-sweep-compact에 16초 소요
- 향후 트래픽 증가하면 또 문제 발생

메모리를 주면 근본 해결 아님 (근본 원인은 설계)
```

**JPA batch size를 1000으로 설정하는 경우:**
```
문제 해결? 근본적 개선이다.

findAll() → batch(1000) 처리:

1차 배치 (Order 1~1000):
→ 1차 배치 객체들만 Young에 할당
→ Young GC로 충분히 정리 가능
→ Old Generation으로 거의 승격 안 됨

2차 배치 (Order 1001~2000):
→ 1차 배치는 이미 DB 전송 완료 → null 처리
→ 1차 객체들이 Young GC에서 회수됨 (10~50ms)
→ 2차 객체들을 같은 공간에 할당

...계속...

메모리 사용량: 상수 (batch size 수준)
GC Pause: Young GC만, 매우 짧음 (~50ms)
```

**GC 관점의 핵심 차이:**

```
힙 확대:
- Young Gen threshold 커짐
- 더 많은 객체를 Old로 승격
- Old Gen의 '산 객체' 증가
- Full GC의 대상 양 증가
- → Pause time 증가

배치 처리:
- 처리 완료된 batch는 즉시 GC root에서 제외
- Young Generation 범위 내에서만 GC 발생
- 일반적으로 10배 이상 짧은 pause time
- Old Generation 압력 거의 없음
```

#### Q4: 힙을 늘렸을 때의 올바른 판단 기준

**단계적 확장:**

```
Step 1: 현재 상태 진단 (필수)
$ jstat -gc -h10 <PID> 1000
```

**해석할 지표:**

```
실시간 모니터링:
- Young GC 빈도: 1분에 몇 회인가?
  (정상: 1분에 2~3회)
- Full GC 빈도: 1일에 몇 회인가?
  (정상: 0회 또는 1회 이하)
- Old Gen 사용률: %로 얼마나 찼는가?
  (정상: 30~60%, 90% 이상 위험)
- GC Pause Time: Young/Old 각각
  (정상: Young <50ms, Old <500ms)
```

**올바른 확장 계획:**

```
Option 1: 힙을 2GB → 3GB로 확대
-Xmx3g -Xms3g
→ Young: 750MB, Old: 2.25GB
→ 1달 모니터링
→ Full GC 빈도는? Pause는?

동시에 진행할 작업:
- 배치 크기 최적화 (1000~5000)
- 메모리 누수 검사 (heap dump 분석)
  $ jmap -dump:live,format=b,file=heap.bin <PID>
- Metaspace 모니터링
  $ jstat -gcmetaspace <PID> 1000
```
