**상황 2: 프로덕션 환경의 GC 일시 정지 시간**

Spring Boot API 서버가 평상시 응답시간 50ms 정도인데, 특정 시간대(보통 자정~새벽)에 순간적으로 5초 이상 응답하지 않는 사건이 반복됩니다. 모니터링 도구로 보니 GC가 시작되는 시점과 응답지연이 정확히 일치합니다. Heap 상황을 보니 사용량이 약 70% 정도에서 Full GC가 발생합니다. 개발팀은 "-XX:+UseG1GC"로 변경하면 해결될 거라고 주장하지만, 운영팀은 현재 설정(CMS GC)을 유지하면서 튜닝으로 해결하자고 합니다.

이 상황에서 단순히 "G1GC가 더 좋으니까 바꿔라"는 답이 아니라, 실제로는 어떤 메커니즘의 차이가 있는지, 그리고 왜 응답시간 문제가 Heap 사용률 70%에서 발생하는지를 생각해야 합니다. 또한 GC 알고리즘 변경 없이 튜닝으로 실제 개선이 가능한지, 그렇다면 어떤 지표를 먼저 봐야 하는지 고민해보세요.

**상황 3: JPA N+1 문제와 메모리의 연관성**

주문 조회 API가 있는데, 최근 주문량 증가에 따라 응답시간이 증가하고 있습니다. 코드를 보니 Order 엔티티를 조회한 후 루프에서 order.getItems()를 호출하는 식입니다. 쿼리 로그를 보니 주문 1건당 약 1ms 시간이 소요되는데, 이는 쿼리 자체의 문제라고만 생각하고 있었습니다.

하지만 GC 로그를 함께 분석해보니 이 API 호출 이후 Young Generation에 엄청난 양의 객체가 생성되고 있습니다. 이는 단순한 "쿼리 성능" 문제가 아니라 "메모리 효율성" 문제입니다. 여기서 생각해볼 점은 무엇일까요? Fetch Join이나 @EntityGraph로 해결하면 N+1은 없어지지만, 과연 메모리 관점에서는 어떤 트레이드오프가 생기는지, 그리고 대량 조회 상황에서는 왜 배치 처리나 스트리밍 방식을 고려해야 하는지 고민해보세요.

## 상황 1: Spring Boot 배치 작업의 메모리 누수 의심

### 모범 답안

**더 근본적인 질문:**
"Full GC 빈도가 증가한 것이 아니라, **왜 충분한 메모리가 있는데도 Old Generation으로 객체들이 계속 승격되고 있는가?**"

**현상 분석:**

```
문제의 본질:
- findAll()로 500만 건을 메모리에 올림
- 필요한 데이터: 300MB, 설정된 Heap: 2GB
- 여유가 있는데도 Full GC 증가 → 메모리 누수 X, 설계 문제 O
```

**GC 로그 해석:**

```
Young Gen 객체들의 비율 분석:
┌─────────────────────────────────────────┐
│ Young Gen 객체 (단기 생존)               │
│  - JPA Entity 인스턴스들                │
│  - 쿼리 결과 캐싱 객체                  │
│  - 임시 처리 객체들                     │
│                                         │
│ → 대부분 Minor GC에서 해제되어야 함    │
└─────────────────────────────────────────┘

Old Gen으로의 승격 비율 증가:
┌─────────────────────────────────────────┐
│ 원인: Weak Generational Hypothesis 위반│
│ - 객체들이 장시간 메모리에 머물러 있음 │
│ - JPA 1차 캐시(Session-level cache)     │
│   에 엔티티가 계속 누적                 │
│                                         │
│ 결과: Old Gen 수거 필요 → Full GC 증가 │
└─────────────────────────────────────────┘
```

**코드 설계 문제 드러내기:**

```java

for (Order order : orders) {
    // 처리
}
// → 500만 Order 객체가 모두 1차 캐시에 적재
// → Heap 메모리 계속 증가
// → Old Gen으로 승격 시작
```

└──────────────────────────────────────────┘

### 핵심 개념 정리

- **Weak Generational Hypothesis**
  - 대부분의 객체는 생성 직후 곧 죽는다는 가정
  - Young Gen에서 대부분 처리되어야 효율적
  - 이 가정이 깨지면 Old Gen 압력 증가 → Full GC 증가

- **JPA 1차 캐시(Persistence Context)**
  - Session/Transaction 단위로 엔티티 객체 보관
  - `findAll()`로 모든 객체가 캐시에 적재
  - 명시적으로 clear() 하지 않으면 계속 메모리 차지

- **Old Generation 승격 메커니즘**
  ```
  Young Gen → Survivor Space → Old Gen 이동
  (기본 15회 Minor GC 후)
  
  Minor GC가 자주 발생할수록
  승격 속도가 빨라짐
  ```

- **Full GC vs Minor GC**
  - Minor GC: Young Gen만 수거, 보통 50-200ms
  - Full GC: 전체 Heap 수거, 보통 1초 이상 (STW 발생)

### 실무 포인트

**진단 방법:**
```bash
# GC 로그 수집
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log

# jmap으로 Heap 덤프 분석
jmap -heap <pid>
jmap -histo <pid> | head -20  # 객체 수 확인

# YourKit/JProfiler로 1차 캐시 모니터링
```

**해결 방안 (우선순위):**

```java
// 1순위: 배치 처리 + 스트리밍
@Transactional
public void processBatch() {
    // 한 번에 1000건씩 처리
    for (int offset = 0; offset < totalCount; offset += 1000) {
        List<Order> batch = orderRepository
            .findOrdersByRange(offset, 1000);
        processBatch(batch);
        
        // 중요: 1차 캐시 명시적 정리
        entityManager.clear();
    }
}

// 2순위: Fetch 최소화 (필요한 필드만)
@Query("SELECT new com.Order(o.id, o.amount) FROM Order o")
List<OrderDTO> findAllDTO();

// 3순위: 스트리밍 (매우 큰 데이터)
public void processStream() {
    try (Stream<Order> stream = orderRepository.streamAll()) {
        stream.forEach(order -> {
            // 처리
        });
    }
}

// 4순위: 배치 서버 분리
// 배치는 별도 JVM (Heap 512MB) + 주기적 재시작
```

## 상황 2: 프로덕션 환경의 GC 일시 정지 시간

### 모범 답안

**핵심 질문:**
"응답시간 문제는 GC 알고리즘 선택의 문제가 아니라, **Heap 설계와 객체 생성 패턴의 문제**이다. CMS도 G1GC도 70% 이상 차면 문제가 발생한다."

**메커니즘 비교:**

```
┌─────────────────────────────────────────────────────────────┐
│ CMS (Concurrent Mark Sweep) GC                              │
├─────────────────────────────────────────────────────────────┤
│ Young Gen:  ParNew (병렬 처리) → STW 약 50-200ms            │
│ Old Gen:    Concurrent Mark-Sweep                          │
│            - Mark Phase (STW, 짧음): 10-50ms               │
│            - Concurrent Sweep (STW 없음)                   │
│                                                              │
│ 문제점:                                                     │
│  1. Heap이 70%를 넘어가면 Concurrent Mode Failure 발생     │
│  2. CMF 발생 시 Full GC로 전환 (STW 긴 시간)               │
│     → 이때 응답 지연 5초 이상 발생!                        │
│                                                              │
│ 70% 도달
