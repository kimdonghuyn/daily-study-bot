## 📚 모범 답안 & 개념 정리

### 1. 🔧 문제 상황

# 상속과 다형성을 통한 게임 캐릭터 시스템 설계

## 모범 답안

이 문제는 **상속과 다형성**으로 해결할 수 있습니다.

### 1단계: 추상화 - 공통 인터페이스 정의
```java
// 모든 캐릭터의 공통 행동을 정의하는 추상 클래스
public abstract class Character {
    protected String name;
    protected int hp;
    
    // 하위 클래스에서 반드시 구현해야 할 메서드
    public abstract void attack();
    
    public void takeDamage(int damage) {
        this.hp -= damage;
    }
}
```

**핵심**: 모든 캐릭터가 해야 할 일("공격한다")을 추상 메서드로 정의하되, **어떻게 공격하는지는 각 캐릭터가 정한다**는 개념입니다.

### 2단계: 구체적 구현 - 각 캐릭터가 자신의 방식으로 상속
```java
public class Warrior extends Character {
    @Override
    public void attack() {
        System.out.println(name + "이(가) 칼로 베었다! (근거리 공격)");
    }
}

public class Mage extends Character {
    @Override
    public void attack() {
        System.out.println(name + "이(가) 파이어볼을 날렸다! (광역 공격)");
    }
}

public class Archer extends Character {
    @Override
    public void attack() {
        System.out.println(name + "이(가) 화살을 쏘았다! (원거리 공격)");
    }
}
```

### 3단계: 메인 코드 - 다형성을 활용한 통일된 처리
```java
public class GameEngine {
    private List<Character> characters = new ArrayList<>();
    
    // 캐릭터 추가 (어떤 캐릭터든 상관없음)
    public void addCharacter(Character character) {
        characters.add(character);
    }
    
    // 모든 캐릭터에게 공격 명령 - 메인 코드는 변하지 않음!
    public void gameRound() {
        for (Character character : characters) {
            character.attack();  // 다형성! 실제 객체의 타입에 따라 다른 공격 실행
        }
    }
}
```

### 4단계: 사용 - 새로운 캐릭터 추가는 메인 코드 수정 없음
```java
public class Main {
    public static void main(String[] args) {
        GameEngine engine = new GameEngine();
        
        engine.addCharacter(new Warrior());  // 메인 코드는 Warrior라는 구체적인 타입을 모른다
        engine.addCharacter(new Mage());
        engine.addCharacter(new Archer());
        
        engine.gameRound();  // 모든 캐릭터가 각자의 방식으로 공격
        
        // 새로운 캐릭터 100개 추가?
        // 메인 코드는 변하지 않음. Character를 상속받은 클래스만 만들면 된다!
        engine.addCharacter(new Paladin());
        engine.addCharacter(new Necromancer());
        // ... 100개 추가 가능
        
        engine.gameRound();
    }
}
```

## 핵심 개념 정리

### 📌 상속 (Inheritance)
- **목적**: 공통 기능을 부모 클래스에서 정의하고 재사용
- **장점**: 코드 중복 제거, 계층 구조 표현
- **원칙**: IS-A 관계 ("Warrior는 Character이다")

### 📌 다형성 (Polymorphism)
- **목적**: 같은 인터페이스로 다른 동작 구현
- **메커니즘**: 런타임에 실제 객체의 타입에 따라 메서드 결정 (동적 바인딩)
- **효과**: **메인 코드는 구체적 구현을 모르고도 사용 가능**

### 📌 Open/Closed Principle (개방-폐쇄 원칙)
```
✅ 확장에 열려있다: 새 캐릭터 추가 가능
✅ 수정에 닫혀있다: 기존 코드 수정 불필요
```

### 📌 SOLID 원칙 중 관련 원칙들
- **LSP** (Liskov Substitution): Character 타입이면 어떤 캐릭터든 대체 가능
- **DIP** (Dependency Inversion): GameEngine이 구체적 클래스 아닌 추상 클래스에 의존

## 실무 포인트

### 🎯 1. 메인 코드가 변하지 않는 이유
```java
// ❌ 다형성 없이 (문제점)
if (character instanceof Warrior) {
    warrior.swordAttack();
} else if (character instanceof Mage) {
    mage.castSpell();
} else if (character instanceof Archer) {
    archer.shootArrow();
}
// 새 캐릭터 추가 시마다 이곳을 수정해야 함

// ✅ 다형성으로 (해결)
character.attack();  // 이 한 줄로 모든 걸 처리
```

### 🎯 2. 실제 대규모 게임 아키텍처
```java
// 더 복잡한 예시: 스킬 시스템
public abstract class Character {
    public abstract void attack();
    public abstract void useSkill();
    public abstract int calculateDamage();
}

// 팩토리 패턴과 결합
public class CharacterFactory {
    public static Character create(String type) {
        switch(type) {
            case "warrior": return new Warrior();
            case "mage": return new Mage();
            // 새 캐릭터는 여기만 추가
            case "paladin": return new Paladin();
            default: throw new IllegalArgumentException();
        }
    }
}
```

### 🎯 3. 테스트 관점
```java
// 다형성 덕분에 Mock 객체로 테스트 가능
public class MockCharacter extends Character {
    @Override
    public void attack() {
        System.out.println("테스트 공격");
    }
}

// GameEngine을 테스트할 때 실제 캐릭터 대신 Mock 사용 가능
```

### 🎯 4. 주의사항
```java
// ❌ 과도한 상속: 깊은 계층 구조는 유지보수 어려움
Character -> LivingThing -> Monster -> Boss -> FinalBoss // 너무 깊음

// ✅ 합리적인 상속: 인터페이스와 조합
public interface Attackable { void attack(); }
public interface Defendable { void defend(); }
public abstract class Character implements Attackable, Defendable { }
```

## 요약: 왜 이 방식이 좋은가?

| 측면 | 문제 상황 | 해결 후 |
|------|---------|--------|
| **유지보수** | 매번 메인 코드 수정 | 새 클래스만 추가 |
| **확장성** | 캐릭터 100개 = 메인 코드도 100줄 증가 | 메인 코드 불변 |
| **테스트** | 각 캐릭터마다 다른 테스트 로직 필요 | 통일된 인터페이스로 단순화 |
| **실수 위험** | 함수 호출 빠뜨리는 버그 가능성 | 구조적으로 보장 |

**시니어 개발자의 관점**: 이것은 단순히 "코드를 짧게 하는 것"이 아닙니다. **10년 후에도 유지보수할 수 있는 구조를 설계하는 것**입니다. 이것이 디자인 패턴과 SOLID 원칙이 존재하는 이유입니다.
