# @Transactional 전파 수준과 롤백 - 모범 답안

## 메인 질문 답변

### 모범 답안

`REQUIRES_NEW`는 **완전히 독립적인 트랜잭션 컨텍스트를 생성**하기 때문에 부모의 롤백으로부터 격리됩니다. 이는 **의도적인 설계**이며, 올바르게 사용하면 강력하지만 오용하면 데이터 일관성을 심각하게 훼손합니다.

```java
// ❌ 위험한 예시
@Service
public class OrderService {
    
    @Transactional
    public void processOrder(Order order) {
        // 주문 저장
        orderRepository.save(order);
        
        // ⚠️ REQUIRES_NEW로 인해 독립적으로 커밋됨
        recordAuditLog(order);  // 부모 롤백 후에도 로그 남음
        
        // 예외 발생 → 주문은 롤백되지만 로그는 커밋됨
        throw new RuntimeException("Payment failed");
    }
    
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordAuditLog(Order order) {
        auditRepository.save(new AuditLog(order));
    }
}
```

**의도적으로 필요한 경우:**

1. **모니터링/로깅 - 실패해도 기록되어야 함**
   ```java
   @Transactional(propagation = Propagation.REQUIRES_NEW)
   public void recordMetrics(String eventType) {
       // 비즈니스 로직 실패와 무관하게 모니터링 기록
       metricsRepository.save(new Metric(eventType));
   }
   ```

2. **외부 시스템 연동 - 재시도 가능성**
   ```java
   @Transactional(propagation = Propagation.REQUIRES_NEW)
   public void notifyExternalSystem(OrderEvent event) {
       // 주문 실패해도 외부에 알림 발송 (재시도 가능)
       externalApiClient.notify(event);
   }
   ```

3. **부분 롤백 시나리오 - 결제는 성공하되 주문은 취소**
   ```java
   @Transactional
   public void refundOrder(Order order) {
       refundPayment(order);  // REQUIRES_NEW - 반드시 커밋
       cancelOrder(order);     // 실패 가능
   }
   
   @Transactional(propagation = Propagation.REQUIRES_NEW)
   public void refundPayment(Order order) {
       paymentRepository.save(new Refund(order));
   }
   ```

**초래하는 위험:**

| 위험 요소 | 설명 | 심각도 |
|---------|------|-------|
| **데이터 불일치** | 주문 없는 결제, 결제 없는 배송 기록 | 🔴 매우높음 |
| **감사 추적 부정확성** | 실패한 작업도 성공으로 기록 | 🟠 높음 |
| **비즈니스 규칙 위반** | 일관성 제약조건 미충족 | 🔴 매우높음 |
| **디버깅 어려움** | 왜 일부만 롤백되는지 파악 곤란 | 🟠 높음 |

### 모범 답안

`REQUIRES_NEW`에서 예외 발생 시 **명시적으로 예외를 던지거나 예외 변환**하여 부모까지 전파시켜야 합니다. 하지만 이렇게 하면 독립성이 훼손되므로 **아키텍처 수준의 재고**가 필요합니다.

```java
// ❌ 단순 재던지기 (문제점 있음)
@Transactional
public void processOrder(Order order) {
    try {
        validateAndSaveOrder(order);
        notifyCustomer(order);  // REQUIRES_NEW
    } catch (RuntimeException e) {
        // 이미 notifyCustomer는 커밋됨
        throw e;  // 부모만 롤백
    }
}

// ✅ 더 나은 방식 1: 결과 검증
@Transactional
public void processOrder(Order order) {
    validateAndSaveOrder(order);
    
    boolean notificationSuccess = notifyCustomerSafely(order);
    if (!notificationSuccess) {
        throw new OrderProcessingException("Notification failed - rolling back order");
    }
}

@Transactional(propagation = Propagation.REQUIRES_NEW, 
               noRollbackFor = {ExternalApiException.class})
public void notifyCustomer(Order order) {
    // 외부 API 호출 - 실패 가능
    externalApiClient.sendEmail(order);
}
