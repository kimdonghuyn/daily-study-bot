## 질문 1: 배치 시스템의 Full GC 문제

### 모범 답안

**먼저 의심해야 할 것: JPA 1차 캐시의 메모리 누적**

이 상황에서 Full GC가 발생하는 핵심 원인은 **메모리 크기가 아니라 영속성 컨텍스트의 생명주기**입니다.

```
문제 상황 분석:
┌─────────────────────────────────┐
│ for 루프 (500만 건)              │
├─────────────────────────────────┤
│ 1. 트랜잭션 시작                 │
│ 2. insert → JPA가 엔티티를 1차캐시에 저장  │
│ 3. insert → 1차캐시에 또 저장    │
│ ...                             │
│ 500만 번: 1차캐시가 500만 개 객체│
│          (all reachable)        │
├─────────────────────────────────┤
│ Young 영역: 빠르게 꽉 찬다       │
│ → Minor GC가 계속 발생           │
│ → 오래된 객체들이 Old 영역으로   │
│    승격(promotion)              │
│ → Old 영역이 가득 찬다          │
│ → Full GC 발생                  │
└─────────────────────────────────┘
```

**스택 vs 힙 메모리 관점:**

```java
// 스택 (Stack Memory)
void processBatch() {  // 메서드 호출 → 스택 프레임 생성
    EntityManager em = ...; // 스택에 참조 저장
    for (int i = 0; i < 5_000_000; i++) {
        Order order = new Order(); // 힙에 객체 생성
        em.persist(order);         // em의 1차캐시에 저장
        // 스택의 order 변수는 reachable 상태 유지
        // 각 루프에서 order 변수는 재사용되지만,
        // 힙의 실제 객체는 1차캐시 때문에 GC 불가능
    }
}

// 힙 (Heap Memory)
// PersistenceContext (EntityManager 내부)
{
    Map<EntityKey, Object> identityMap = new HashMap<>();
    // 500만 개의 Order 객체가 모두 identityMap에 저장됨
    // → Old 영역 압박 → Full GC
}
```

**해결책:**

```java
// ❌ 틀린 방법: -Xmx만 크게 늘리기
// java -Xmx8g -Xms8g BatchApplication

// ✅ 올바른 방법: 배치 처리 최적화
@Transactional
public void processBatchOptimized() {
    int batchSize = 1000;
    
    for (int i = 0; i < 5_000_000; i += batchSize) {
        // 1. 내부 트랜잭션 사용
        processBatchChunk(i, batchSize);
        
        // 2. 영속성 컨텍스트 초기화
        em.clear(); // 또는 em.flush(); em.clear();
    }
}

@Transactional
private void processBatchChunk(int start, int size) {
    for (int i = start; i < start + size; i++) {
        Order order = new Order();
        orderRepository.save(order);
    }
    // 메서드 종료 시 영속성 컨텍스트도 종료
}

// ✅ 더 나은 방법: Batch Insert 쿼리 직접 사용
public void processBatchBulk() {
    List<Order> batch = new ArrayList<>(1000);
    
    try (var connection = dataSource.getConnection()) {
        String sql = "INSERT INTO orders (...) VALUES (?, ...)";
        var statement = connection.prepareStatement(sql);
        
        for (int i = 0; i < 5_000_000; i++) {
            // 값 설정
            statement.setString(1, ...);
            statement.addBatch();
            
            if (i % 1000 == 0) {
                statement.executeBatch();
                statement.clearBatch();
            }
        }
        statement.executeBatch();
    }
    // JPA 1차캐시 사용 안 함 → Young 영역 압박 최소화
}
```

### 핵심 개념 정리

- **1차 캐시 (Identity Map Pattern)**
  - `EntityManager`가 관리하는 영속성 컨텍스트 내의 메모리 캐시
  - 트랜잭션이 살아있는 동안 모든 엔티티는 GC 불가능(reachable)
  - 메모리에 적재된 객체 수 = 나중에 Old 영역으로 승격되는 객체 수

- **세대별 GC (Generational GC)**
  - Young: 단기 객체 저장, 빠른 GC (mark-sweep)
  - Old: 장기 객체 저장, 느린 GC (mark-sweep-compact)
  - Promotion: Young에서 오래 살아남은 객체가 Old로 이동

- **Full GC vs Minor GC**
  - Minor GC (Young GC): 수 ms, 자주 발생 → 괜찮음
  - Full GC: 수백 ms, 드물게 발생 → 응답시간 SLA 위반
  - Full GC 빈도 ∝ Old 영역 채우는 속도

- **메모리 누수 vs 영속성 컨텍스트 누적**
  - 메모리 누수: unreachable 객체가 GC 불가능 (버그)
  - 이 경우: reachable 객체가 계속 누적 (설계 문제)

```

    ↓

```

- 주기: 처리량과 메모리를 고려해 결정
- 로깅: 진행률, 처리시간, GC 발생 여부 모니터링
