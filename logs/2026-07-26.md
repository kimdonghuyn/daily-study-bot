# 상속과 다형성: 게임 캐릭터 공격 시스템

## 모범 답안

이 문제는 **상속과 다형성**으로 우아하게 해결됩니다.

### 문제 분석
- **현재 문제**: 같은 의미의 작업(공격)을 여러 함수로 구현 → 타입 체크 필수 → 새 타입 추가 시 기존 코드 수정
- **핵심 원인**: 구체적인 구현에 의존 + 개방-폐쇄 원칙(OCP) 위반

### 해결책: 상속 + 다형성

```python
# 1️⃣ 부모 클래스: 공통 인터페이스 정의
from abc import ABC, abstractmethod

class Character(ABC):
    def __init__(self, name, hp):
        self.name = name
        self.hp = hp
    
    @abstractmethod
    def attack(self) -> str:
        """각 캐릭터의 공격 방식을 정의"""
        pass
    
    def take_damage(self, damage):
        self.hp -= damage
        print(f"{self.name}이(가) {damage}의 피해를 입었습니다. (남은 HP: {self.hp})")

# 2️⃣ 자식 클래스: 각각의 공격 방식 구현
class Warrior(Character):
    def attack(self) -> str:
        return f"{self.name}이(가) 강력한 칼질을 날립니다! ⚔️"

class Mage(Character):
    def attack(self) -> str:
        return f"{self.name}이(가) 파이어볼을 시전합니다! 🔥"

class Archer(Character):
    def attack(self) -> str:
        return f"{self.name}이(가) 정확한 화살을 쏩니다! 🏹"

# 3️⃣ 게임 로직: 타입 확인 없이 동작
class Game:
    def __init__(self):
        self.characters: list[Character] = []
    
    def add_character(self, character: Character):
        self.characters.append(character)
    
    def execute_all_attacks(self):
        """모든 캐릭터에게 attack() 호출 - 타입 확인 불필요!"""
        for character in self.characters:
            print(character.attack())  # 다형성: 같은 호출, 다른 실행

# 4️⃣ 사용
game = Game()
game.add_character(Warrior("아서", 100))
game.add_character(Mage("메를린", 80))
game.add_character(Archer("로빈", 75))

game.execute_all_attacks()

# 출력:
# 아서이(가) 강력한 칼질을 날립니다! ⚔️
# 메를린이(가) 파이어볼을 시전합니다! 🔥
# 로빈이(가) 정확한 화살을 쏩니다! 🏹

# 5️⃣ 새로운 캐릭터 추가 (기존 코드 수정 불필요!) ✨
class Paladin(Character):
    def attack(self) -> str:
        return f"{self.name}이(가) 신성한 빛을 발동합니다! ✨"

game.add_character(Paladin("우서", 110))
game.execute_all_attacks()  # 자동으로 작동!
```

## 핵심 개념 정리

### 상속 (Inheritance)
- **목적**: 공통 속성과 메서드를 부모 클래스에서 정의
- **이점**: 코드 중복 제거, 공통 인터페이스 제공
- 위 예제: `Character` 클래스가 모든 캐릭터의 기본 구조 정의

### 다형성 (Polymorphism)
- **정의**: "같은 메서드 호출이 객체의 실제 타입에 따라 다르게 동작"
- **핵심**: `character.attack()` 한 줄이 각 클래스에서 다르게 실행됨
- **조건**: 부모 클래스의 메서드를 자식 클래스에서 **오버라이드(재정의)**

### 오버라이딩 vs 오버로딩
| 개념 | 설명 | 예제 |
|------|------|------|
| **오버라이드** | 부모 메서드를 자식에서 다시 정의 | Warrior의 `attack()` |
| **오버로드** | 같은 이름, 다른 파라미터 | Python은 미지원 (다른 언어) |

### 개방-폐쇄 원칙 (OCP)
```
확장에는 개방(새 캐릭터 추가 = Character 상속)
수정에는 폐쇄(기존 Game 로직 수정 불필요)
```

### 🎯 시니어 개발자의 관점

1. **유지보수성**: 새 기능 추가 시 기존 코드 수정 최소화
2. **테스트 용이성**: 각 캐릭터를 독립적으로 테스트 가능
3. **확장성**: 100개 캐릭터가 생겨도 메인 로직은 변경 없음
4. **가독성**: `character.attack()`이 의도를 명확히 표현

### 🔧 현장 팁

```python
# 타입 힌트로 계약(Contract) 명시
def game_loop(characters: list[Character]) -> None:
    """Character의 모든 서브클래스를 받을 수 있음"""
    for character in characters:
        character.attack()

# IDE의 자동완성과 타입 체크 지원 → 버그 조기 발견
```

이것이 바로 **SOLID 원칙 중 L(Liskov Substitution Principle)**입니다. 자식 클래스는 부모 클래스를 대체 가능해야 한다는 원칙이죠!
