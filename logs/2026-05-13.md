## 📚 모범 답안 & 개념 정리

### 1. 🔧 문제 상황

# JVM 메모리 구조 - 왜 분리하는가?

## 모범 답안

**JVM이 메모리를 분리하는 이유는 "목적"과 "생명주기"가 다르기 때문입니다.**

### 1️⃣ **각 영역의 역할이 다르다**
- **Stack**: 메서드 호출, 로컬 변수 → **빠른 접근, 자동 정리**
- **Heap**: 객체 생성 → **동적 할당, GC 대상**
- **Method Area**: 클래스 정보, 메서드 코드 → **공유, 한 번만 로드**

### 2️⃣ **메모리가 하나였다면?**

```
❌ 문제 1: 접근 속도 저하
- Stack처럼 빠른 접근이 필요한 데이터와
- Heap처럼 동적으로 움직이는 데이터를
- 같은 관리 정책으로 처리하면 성능 저하

❌ 문제 2: 메모리 단편화 심각
- 객체 생성/삭제로 인한 단편화
- 메서드 호출 시 필요한 연속적 메모리 확보 어려움

❌ 문제 3: 가비지 컬렉션 비효율
- 불필요한 전역 GC 실행
- Stack 영역까지 스캔하는 낭비

❌ 문제 4: 스레드 안정성
- Stack은 스레드 독립적(각 스레드가 자신의 Stack 보유)
- 하나의 메모리면 동기화 오버헤드 극심
```

### 3️⃣ **실제 상황 적용**

당신의 OutOfMemoryError는:

```java
// ❌ Heap 부족 예시
List<String> cache = new ArrayList<>();
while(true) {
    cache.add(new String("data")); // 계속 객체 생성
}
// → Heap 용량 초과

// ❌ Stack 부족 예시
void recursion(int n) {
    recursion(n+1); // 무한 재귀
}
// → Stack Overflow (StackOverflowError)

// ✅ 정상 상황
int localVar = 10;           // Stack에 저장 (빠름, 자동 정리)
User user = new User(...);   // Heap에 저장 (GC 대상)
```

## 핵심 개념 정리

### 📌 **Stack 영역**
```
특징:
- LIFO (Last In First Out) 구조
- 메서드 호출 시 Frame 생성, 반환 시 자동 제거
- 각 스레드마다 독립적인 Stack 보유
- 고정 크기 (보통 1MB~)

저장 내용:
- 메서드 호출 정보
- 로컬 변수 (원시 타입)
- 객체 참조값 (주소)

에러:
- StackOverflowError: 재귀 깊이 초과
```

### 📌 **Heap 영역**
```
특징:
- 모든 스레드가 공유
- 동적 크기 할당/해제
- GC 관리 대상
- 크기 제한 (보통 수십 GB)

저장 내용:
- 모든 객체 인스턴스
- 배열
- 클래스 인스턴스 변수

에러:
- OutOfMemoryError: Heap 용량 초과
```

### 📌 **Method Area (Metaspace in Java 8+)**
```
특징:
- 모든 스레드가 공유
- 런타임 상수 풀, 필드 데이터, 메서드 코드
- Java 8 이후 Native Memory 사용 (크기 제한 완화)
- 클래스 로딩 시 생성, 언로딩까지 유지

에러:
- OutOfMemoryError: Metaspace (클래스 로딩 과다)
```

## 실무 포인트

### 🔍 **문제 진단 방법**

```bash
# OutOfMemoryError 원인 파악
jps                    # JVM 프로세스 확인
jmap -heap <pid>       # Heap 상태 분석
jstack <pid>           # Thread 정보 (Stack overflow 유무)

# 메모리 설정값 확인
jinfo -flag -Xmx <pid>   # Maximum Heap Size
jinfo -flag -Xss <pid>   # Stack Size
```

### 💡 **실전 대응 방법**

```java
// 1️⃣ Heap 부족 → 메모리 누수 찾기
@Transactional
public void processLargeData() {
    // ❌ 나쁜 예
    List<User> users = userRepository.findAll(); // 모두 로드
    
    // ✅ 좋은 예
    userRepository.findAll(PageRequest.of(0, 1000)) // 페이징
        .forEach(user -> processUser(user));
}

// 2️⃣ Stack 부족 → 깊은 재귀 제거
// ❌ 깊은 재귀
private int factorial(int n) {
    if(n == 0) return 1;
    return n * factorial(n-1);
}

// ✅ 반복문 또는 스트림
private int factorial(int n) {
    int result = 1;
    for(int i = 2; i <= n; i++) result *= i;
    return result;
}

// 3️⃣ JVM 옵션 조정
// java -Xmx2048m -Xms1024m -Xss512k -jar app.jar
// -Xmx: 최대 Heap 크기
// -Xms: 초기 Heap 크기
// -Xss: Stack 크기 (스레드당)
```

### 📊 **모니터링 체크리스트**

| 영역 | 모니터링 항목 | 정상 범위 |
|------|------------|---------|
| **Heap** | Used/Max 비율 | < 70% |
| **Heap** | GC 빈도 | 분 단위 이상 |
| **Stack** | 동시 스레드 수 | < 1000 |
| **Metaspace** | 로드된 클래스 수 | 정상 범위 내 |

### 🎯 **시니어 관점의 조언**

```
1. "Heap이 부족하다" ≠ 단순히 메모리 크기 증가
   → 메모리 누수, 캐시 정책, 배치 크기 검토

2. "Stack도 체크해봐야 한다" = 스레드 구조 재검토
   → 재귀 깊이, 동시 스레드 수, 콜 스택 분석

3. 분리된 메모리 구조 = 분리된 대응 전략
   → 각 영역의 특성을 이해한 최적화 필요
```

**결론**: JVM의 메모리 분리는 **성능**과 **안정성**을 동시에 확보하기 위한 설계입니다. 통합 메모리는 구현은 단순하지만, 실제 운영 환경에서는 수많은 문제를 야기합니다.
