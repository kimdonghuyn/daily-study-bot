## 상황 1: Spring Boot 배치 애플리케이션의 메모리 폭증 문제

### 📖 모범 답안

**"Heap 크기 증가는 증상 치료, 배치 처리 방식 개선은 근본 치료입니다."**

#### 1. 우선순위: 처리 방식 개선이 먼저
- **Heap 확대의 한계**: 24GB → 48GB → 무한 확대의 악순환. 결국 GC 자체가 병목
- **정상적인 배치 설계**: 메모리는 비용, 배치 로직에서 **필요한 것만 필요한 만큼** 로드

#### 2. GC 관점 비교 분석

| 구분 | findAll() 방식 | 페이징/스트리밍 |
|------|---|---|
| **Young Gen 객체 생성** | 100만 개 동시 생성 → 빈번한 Minor GC | 배치당 1만 개씩 생성 → 상대적으로 적음 |
| **Old Gen 생존율** | 처리 중인 객체들이 Old Gen 진입 → Full GC 유발 | 배치 완료 후 즉시 GC 대상 → 효율적 |
| **GC Pause Time** | 100만 개 객체 추적 → 수초 ~ 수십초 | 1만 개 객체 추적 → 밀리초 단위 |
| **메모리 단편화** | 심각 → Heap fragmentation | 미미 |

**구체적 예시:**
```
findAll() 방식 GC 로그:
[Full GC (System.gc()) 12345K->8901K(24576K), 5.234 secs]
           ↑ 12GB 추적, 5초 pause time

페이징 방식 GC 로그:
[GC (Allocation Failure) 256K->128K(2048K), 0.034 secs]
       ↑ 256KB 추적, 34ms pause time
```

#### 3. GC 로그 분석 포인트

```bash
# JVM 옵션으로 상세 GC 로그 수집
-Xms4G -Xmx4G \
-XX:+PrintGCDetails \
-XX:+PrintGCDateStamps \
-XX:+PrintGCApplicationStoppedTime \
-Xloggc:/logs/gc.log
```

**분석해야 할 지표:**
```
1. Full GC 발생 빈도 (초당/분당)
   - 1분에 10회 이상 → 심각한 메모리 압박
   - findAll()은 보통 분에 수십 회 발생

2. GC Pause Time
   - Young GC: 50ms 이상 → 문제
   - Full GC: 1초 이상 → 매우 위험

3. Heap 사용량 추세
   - 계속 상승 후 수직 낙하: 정상적인 GC
   - 미세한 상승만 반복: Old Gen 누적 의심

4. GC 효율성
   - Full GC 후 회수된 메모리량
   - 회수량이 50% 이하 → 메모리 부족 신호
```

### 💡 핵심 개념 정리

- **GC의 근본 원리**: GC는 도움이 아닌 필요악. 발생 자체를 최소화하는 설계가 1순위
- **Young/Old Generation 역할**:
  - Young Gen: 대부분 객체가 죽음 (98% 소멸) → 빠른 Minor GC 적합
  - Old Gen: 장기 생존 객체 → Full GC는 비용이 큼
- **메모리 압박 신호**: Full GC 빈도 증가 = 애플리케이션 설계 재검토 신호

### 🔧 실무 포인트

// Repository

**✅ 올바른 방식 3: Spring Batch (가장 권장)**
```java
@Configuration
@EnableBatchProcessing
public class BatchConfig {
    
    @Bean
    public Job processBatchJob(
            ItemReader<Order> reader,
            ItemProcessor<Order, Order> processor,
            ItemWriter<Order> writer) {
        return jobBuilderFactory.get("processBatchJob")
            .start(stepBuilderFactory.get("processOrderStep")
                .<Order, Order>chunk(10000) // 청크 사이즈
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .build())
            .build();
    }
}
```

- Heap: 4GB로 충분

## 상황 2: 동시 사용자 급증 시 응답 시간 저하

### 📖 모범 답안

**"Full GC 빈도 증가는 Young Generation이 포화되었다는 신호입니다. 메모리가 남아있어도 발생합니다."**

#### 1. 왜 메모리가 충분한데 Full GC가 자주 발생할까?

**핵심 메커니즘:**
```
동시 사용자 100명 → 1000명으로 증가

Young Generation 할당 요청량:
- 요청당 평균 1MB 객체 생성
- 100명: 분당 6000MB 생성 (GC 대기 시간 충분)
- 1000명: 분당 60000MB 생성 (Young Gen 금방 차버림)

결과: Young Gen이 금방 찬다 → 승격 규칙 발동
      → 미성숙 객체까지 Old Gen으로 넘어감
      → Old Gen 압박 → Full GC 필요
```

**구체적 타이밍:**
```
요청 1: User 1, 요청 2: User 2, ... 요청 1000: User 1000
  ↓
모두 Young Gen에 객체 할당 중
  ↓
Young Gen 한계치 도달 (예: 1GB)
  ↓
기존: Minor GC 완료 후 처리 계속
지금: 아직 처리 중인 객체도 있는데 승격 필요
  ↓
Old Gen 메모리 부족 징후
  ↓
Full GC 발동 (Stop-The-World)
```

#### 2. Young/Old Generation 역할 재정의

```
┌─────────────────────────────────────┐
│          Heap (8GB 예시)            │
├──────────────┬──────────────────────┤
│
