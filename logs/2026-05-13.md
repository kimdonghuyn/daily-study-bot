### 1. 🔧 문제 상황

# JVM 메모리 구조: 왜 분리되어 있을까?

## 모범 답안

### 핵심 요약
JVM이 메모리를 분리하는 이유는 **데이터의 생명주기, 접근 패턴, 성능 특성이 완전히 다르기 때문**입니다.

### 상세 설명

**1. Heap과 Stack을 나누는 이유**

```java
public class MemoryExample {
    public static void main(String[] args) {
        int age = 25;              // Stack: 원시타입, 고정 크기
        String name = new String("John");  // Stack: 참조값, Heap: 실제 객체
        
        processUser(age, name);
    }
    
    private static void processUser(int age, String name) {
        User user = new User(age, name);  // 메서드 종료 시 Stack은 자동 정리
    }
}
```

| 구분 | Stack | Heap |
|-----|-------|------|
| 생명주기 | 메서드 호출/종료 시 자동 정리 | GC가 정리할 때까지 유지 |
| 크기 | 작고 고정됨 | 크고 동적 |
| 접근 | 매우 빠름 (순차적) | 상대적으로 느림 |
| 멀티스레드 | 스레드마다 독립적 | 모든 스레드가 공유 |

**만약 메모리가 하나였다면?**

```
❌ 문제점 1: 메모리 회수 불가능
- Stack처럼 자동 정리 vs Heap처럼 GC 필요
- 어떤 방식을 선택하든 비효율적

❌ 문제점 2: 스택 오버플로우 감지 불가
- 무한 재귀 호출이 끝까지 진행되어 시스템 전체 마비
- 지금은 Stack 영역을 초과하면 즉시 StackOverflowError 발생

❌ 문제점 3: 성능 저하
- 작은 변수들도 GC 대상이 되어 GC 압력 증가
- 메모리 fragmentation 심화
```

## 핵심 개념 정리

### 📌 JVM 메모리 3대 영역

#### 1️⃣ **Stack (스택)**
- **용도**: 메서드 호출, 원시타입 변수, 참조값 저장
- **특징**: LIFO(Last-In-First-Out), 스레드당 독립적
- **크기**: 고정 (기본 -Xss 1MB)
- **정리**: 자동 (메서드 반환 시)
- **예외**: `StackOverflowError` (깊은 재귀)

#### 2️⃣ **Heap (힙)**
- **용도**: 모든 객체, 배열 인스턴스 저장
- **특징**: 모든 스레드가 공유, 동적 할당
- **크기**: 동적 (-Xmx로 설정)
- **정리**: Garbage Collector 담당
- **예외**: `OutOfMemoryError: Java heap space`

#### 3️⃣ **Method Area (메서드 영역)**
- **용도**: 클래스 구조, 메서드 데이터, 생성자, 메서드 코드 저장
- **특징**: 클래스당 1회 로드, 모든 스레드 공유
- **크기**: JVM 구현에 따라 다름 (-XX:MetaspaceSize)
- **정리**: Class Unloading 시 (거의 안함)
- **예외**: `OutOfMemoryError: Metaspace`

### 💡 메모리 분리의 이점

```
┌─────────────────────────────────────┐
│         JVM 메모리 분리의 목적       │
├─────────────────────────────────────┤
│ 1. 생명주기 관리 최적화              │
│    → Stack: 자동, Heap: GC 관리     │
│                                     │
│ 2. 성능 최적화                      │
│    → Stack: O(1) 할당/해제          │
│    → Heap: 복잡하지만 필요시만 GC   │
│                                     │
│ 3. 멀티스레딩 안전성                 │
│    → Stack: 스레드 격리              │
│    → Heap: 동기화로 보호             │
│                                     │
│ 4. 메모리 누수 감지                  │
│    → Stack overflow 즉시 감지       │
│    → Heap overflow 차등 처리         │
└─────────────────────────────────────┘
```

```bash

```

### 💻 실제 문제 해결 예시

**상황**: Heap은 여유 있는데 OutOfMemoryError 발생

```java
// ❌ Stack Overflow 사례
public class RecursionBomb {
    static int count = 0;
    
    public static void boom() {
        count++;
        boom();  // 스택이 쌓여서 StackOverflowError 발생!
    }
}

// ✅ 해결
public static void boom(int depth) {
    if (depth > MAX_DEPTH) {
        throw new IllegalArgumentException("너무 깊음");
    }
    boom(depth + 1);
}
```

### 📊 JVM 옵션 튜닝 가이드

```bash
# Heap 관련
-Xms2G          # 초기 Heap 크기
-Xmx8G          # 최대 Heap 크기
-XX:+UseG1GC    # G1 GC 사용 (권장)

# Stack 관련
-Xss1M          # 스레드당 Stack 크기

# Method Area (Java 8+)
-XX:MetaspaceSize=64M
-XX:MaxMetaspaceSize=512M

# 모니터링
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:gc.log
```
