## 📚 모범 답안 & 개념 정리

### 1. 🔧 문제 상황

# 상속과 다형성: 배달 앱 시스템 설계

## 모범 답안

이 상황에서는 **상속(Inheritance)**과 **다형성(Polymorphism)**을 활용해야 합니다.

### 설계 방식:

1. **기본 클래스 (부모 클래스) 설계**
   - `Delivery` 또는 `DeliveryService`라는 추상 클래스를 만들고
   - 공통 프로세스(출발, 배달 중, 완료)를 구현

2. **구체적 클래스 (자식 클래스) 설계**
   - `MotorbikeDelivery` → 오토바이 배달 클래스
   - `BicycleDelivery` → 자전거 배달 클래스
   - 각각 **준비 과정만 다르게 구현**

3. **핵심 원리**
   - 공통 부분(배달 프로세스)은 **상속으로 재사용**
   - 다른 부분(준비 과정)은 **메서드 오버라이딩으로 다형성 구현**

```
Delivery (부모)
├─ prepare() → 추상 메서드 (구현 강제)
├─ startDelivery() → 공통 로직
├─ inDelivery() → 공통 로직
└─ completeDelivery() → 공통 로직

MotorbikeDelivery (자식)
└─ prepare() → "휘발유 주입" 구현

BicycleDelivery (자식)
└─ prepare() → "체인 정비" 구현
```

## 핵심 개념 정리

### 📌 상속 (Inheritance)
- **정의**: 부모 클래스의 속성과 메서드를 자식 클래스가 물려받는 것
- **이점**: 
  - 코드 중복 제거 → `startDelivery()`, `completeDelivery()` 한 번만 작성
  - 유지보수 용이 → 공통 로직 수정 시 한 곳만 변경
  - 계층 구조로 논리적 관계 표현 가능

### 📌 다형성 (Polymorphism)
- **메서드 오버라이딩**: 부모의 `prepare()`를 자식에서 다르게 구현
- **런타임 바인딩**: 실행 시점에 어떤 `prepare()`를 호출할지 결정
  ```
  Delivery delivery = new MotorbikeDelivery();
  delivery.prepare(); // "휘발유 주입" 실행
  
  delivery = new BicycleDelivery();
  delivery.prepare(); // "체인 정비" 실행
  ```

### 📌 추상 클래스/인터페이스의 역할
- **계약(Contract) 정의**: 모든 배달 방식은 `prepare()`를 구현해야 함
- **타입의 일관성**: 다양한 배달 타입을 하나의 `Delivery` 타입으로 취급 가능
- **강제성**: 자식 클래스가 필수 메서드 구현을 빠뜨리지 않도록 보장

### 📌 DRY 원칙 (Don't Repeat Yourself)
- 코드 중복 최소화
- 유사한 로직은 한 곳에만 작성

## 실무 포인트

### ✅ 현재 상황에서의 이점

| 측면 | 이전 (코드 복사) | 개선 (상속/다형성) |
|------|----------------|------------------|
| **코드량** | 배달 로직 2배 | 배달 로직 1번 작성 |
| **버그 수정** | 두 곳 모두 수정 필요 | 한 곳만 수정 |
| **새 배달 수단 추가** | 전체 로직 다시 작성 | `prepare()` 메서드만 추가 |
| **테스트** | 중복된 테스트 코드 | 공통 로직 테스트 1번 |

### 🚀 실무 확장 시나리오

**초기 설계** (상속/다형성 적용):
```
1단계: Motorbike, Bicycle 추가
2단계: Drone, Car 추가 → prepare() 메서드만 추가
3단계: 배달료 계산 로직 추가 → Delivery 클래스 한 곳만 수정
4단계: 배달 대기열 관리 → Delivery[] 또는 List<Delivery>로 통일 관리
```

**만약 이를 무시했다면**:
- 매번 전체 배달 로직을 복사-붙여넣기
- 배달 로직 수정 시 모든 클래스 변경 필요
- 새 배달 수단 추가 난이도 높음

### 💡 팀 협업 관점

```
👨‍💼 팀장: "모든 배달 방식의 기본 플로우는 이걸로 통일하자"
→ Delivery 추상 클래스 설계

👨‍💻 개발자 A: "오토바이 배달 담당, prepare() 메서드만 구현"
👩‍💻 개발자 B: "자전거 배달 담당, prepare() 메서드만 구현"
→ 병렬 개발 가능, 간섭 최소화
```

### ⚠️ 주의사항

- **과도한 추상화 금지**: 현재는 2가지 배달만 있으면, 무리해서 복잡하게 설계하지 말 것
- **공통점 찾기가 핵심**: 진정한 공통 로직만 추출해야 효과적
- **변경 가능성 고려**: "추후 배달 수단이 계속 늘어날 것 같다"면 상속 구조 적극 추천
