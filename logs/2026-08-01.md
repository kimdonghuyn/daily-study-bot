### 1. 🔧 문제 상황

# 상속과 다형성을 통한 음식 배달 앱 구조 개선

## 모범 답안

**상황 분석:**
지금 코드의 문제는 **반복(Duplication)**과 **수정의 어려움(Maintenance Nightmare)**입니다. 피자, 치킨, 한식의 조리 시간·가격 계산·배달 가능 여부 로직이 흩어져 있고, 새 음식이 추가되면 또 다시 비슷한 코드를 작성해야 합니다.

**상속과 다형성의 해결책:**

1. **상속(Inheritance)** - 공통점을 한곳에 모은다
   - "모든 음식"이 공통으로 가져야 할 속성과 메서드를 `Food` 부모 클래스에 정의
   - 피자, 치킨, 한식은 `Food`를 상속받아 **공통 코드 중복을 제거**

2. **다형성(Polymorphism)** - 음식마다 다른 동작을 자유롭게 구현한다
   - 각 음식이 `조리시간()`, `가격계산()`, `배달가능여부()`를 **자신의 방식으로 구현**
   - 메인 로직은 음식의 종류를 신경 쓰지 않고 `Food` 타입으로 처리

**결과:**
```
❌ 이전: 피자 로직 → 복사 → 치킨 로직 → 복사 → 한식 로직
✅ 이후: Food 부모 클래스 정의 → 각 음식이 상속 + 구현 → 메인 로직은 그대로
```

## 핵심 개념 정리

### 1️⃣ **상속 (Inheritance)**
- **목적**: 코드 중복 제거, DRY 원칙 준수
- **역할**: 공통 속성과 메서드를 부모 클래스에 한번만 작성
- **예시**:
  ```java
  // 공통 속성/메서드
  abstract class Food {
      String name;
      int basePrice;
      
      abstract int getCookingTime();  // 각 음식마다 다름
      abstract int calculatePrice();  // 각 음식마다 다름
  }
  
  class Pizza extends Food { /* 피자만의 로직 */ }
  class Chicken extends Food { /* 치킨만의 로직 */ }
  ```

### 2️⃣ **다형성 (Polymorphism)**
- **목적**: 같은 인터페이스로 다양한 객체를 처리
- **종류**: 
  - **메서드 오버라이딩** (Runtime Polymorphism)
  - **메서드 오버로딩** (Compile-time Polymorphism)
- **실무 이점**: 메인 로직이 음식 종류를 일일이 체크할 필요 없음

### 3️⃣ **실제 코드 비교**

#### ❌ 상속/다형성 없는 코드 (코드 악취)

#### ✅ 상속/다형성 적용한 코드 (깔끔하고 확장 가능)
```java
// 1. 부모 클래스 (공통 인터페이스 정의)
public abstract class Food {
    protected String name;
    protected int basePrice;
    
    abstract int getCookingTime();
    abstract int calculatePrice(int quantity);
    abstract boolean isDeliverable(int distance);
}

// 2. 각 음식 구현 (음식마다 다른 로직만 작성)
public class Pizza extends Food {
    public Pizza() { 
        this.name = "Pizza"; 
        this.basePrice = 12000; 
    }
    
    @Override
    public int getCookingTime() { return 15; }
    
    @Override
    public int calculatePrice(int quantity) { 
        return quantity * basePrice; 
    }
    
    @Override
    public boolean isDeliverable(int distance) { 
        return distance <= 5; 
    }
}

public class Chicken extends Food {
    public Chicken() { 
        this.name = "Chicken"; 
        this.basePrice = 15000; 
    }
    
    @Override
    public int getCookingTime() { return 20; }
    
    @Override
    public int calculatePrice(int quantity) { 
        return quantity * basePrice; 
    }
    
    @Override
    public boolean isDeliverable(int distance) { 
        return distance <= 8; 
    }
}

// 3. 메인 로직 (음식 종류를 신경 쓰지 않음!)
public class FoodDeliveryService {
    public void processOrder(Food food, int quantity, int distance) {
        System.out.println("조리 시간: " + food.getCookingTime() + "분");
        System.out.println("가격: " + food.calculatePrice(quantity) + "원");
        System.out.println("배달 가능: " + food.isDeliverable(distance));
    }
}

// 4. 사용
Food pizza = new Pizza();
Food chicken = new Chicken();
Food korean = new KoreanFood();

deliveryService.processOrder(pizza, 2, 4);      // 자동으로 Pizza 로직 실행
deliveryService.processOrder(chicken, 1, 6);    // 자동으로 Chicken 로직 실행
deliveryService.processOrder(korean, 3, 2);     // 자동으로 KoreanFood 로직 실행
```

## 실무 포인트

### 🎯 **개발 생산성 향상**
| 항목 | 상속 전 | 상속 후 |
|------|--------|--------|
| 새 음식 추가 시간 | 15~20분 (여러 메서드 복사) | 3~5분 (클래스 1개만 작성) |
| 버그 발생 위험 | 높음 (복사 실수) | 낮음 (공통 로직은 이미 검증됨) |
| 기존 코드 수정 | 모든 음식별로 수정 필요 | 부모 클래스만 수정 |

### 🔄 **변경에 유연한 코드**
```java
// 예: 모든 음식의 기본 가격을 10% 인상
❌ 수정 전: if-else 블록 모두에서 * 1.1 추가
✅ 수정 후: Food 클래스의 basePrice 계산 로직만 수정

// 배달 거리 제한 규칙 변경
❌ 수정 전: 모든 음식의 isDeliverable() 메서드 수정
✅ 수정 후: 각 음식 클래스에서만 필요한 부분만 수정
```

### 📋 **SOLID 원칙 준수**
- **Open/Closed Principle**: 새 음식 추가에는 열려있고(Open), 기존 코드 수정에는 닫혀있음(Closed) ✅
- **Liskov Substitution**: 모든 Food 자식은 부모처럼 사용 가능 ✅
- **Dependency Inversion**: 구체적인 Pizza/Chicken이 아닌 추상 Food에 의존 ✅
