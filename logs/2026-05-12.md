## 질문 1: 배치 시스템의 점진적 성능 저하 원인 분석

### 모범 답안

**근본 원인 분석:**

이 현상은 **메모리 단편화(Memory Fragmentation)**와 **Old Generation의 증가로 인한 Full GC 빈도 증가**가 원인입니다.

```
초기 상태(30분)
┌─────────────────────────────┐
│ Young Gen (빠른 GC)         │ ← 데이터 처리 중 생성되는 임시 객체들
│ Old Gen (여유있음)          │ ← 필요한 객체들만 저장
└─────────────────────────────┘
GC Pause: ~1-2초

3개월 후(45분)
┌─────────────────────────────┐
│ Young Gen (비효율적)        │ ← 단편화로 인한 할당 실패
│ Old Gen (차오름)            │ ← 메모리 단편화로 객체 보유
└─────────────────────────────┘
GC Pause: ~5-10초 (Full GC 자주 발생)
```

**구체적 메커니즘:**

1. **300만 건 배치 처리 과정에서의 메모리 사용 패턴**
   ```java
   // 문제 있는 패턴
   List<ResultEntity> allResults = new ArrayList<>();
   
   for(int i = 0; i < 3_000_000; i++) {
       Data data = fetchData(i);
       ProcessedResult result = complexLogic(data);
       allResults.add(result);  // 모두 Old Gen으로 승격
   }
   // 메모리 누적: ~500MB-1GB
   ```

2. **메모리 단편화가 발생하는 이유**
   - 배치 첫 시작: Young Gen에서 임시 객체 생성/소멸 (GC 반복)
   - 처리 진행: 처리 결과들이 Old Gen으로 승격
   - 누적: Old Gen이 단편화된 상태로 차게 됨
   - 문제: 새로운 객체 할당할 메모리가 충분해도 연속된 공간 부족 → Full GC 필요

3. **GC Pause 길어지는 이유**
   ```
   회차별 GC 동작:
   1차 배치: Young GC (200ms) → Full GC (2초)
   2차 배치: Young GC (300ms) → Full GC (3초)
   3차 배치: Young GC (400ms) → Full GC (4초)
   ...
   최근: Young GC (500ms) → Full GC (7초) × 여러 번
   ```

**왜 단순히 힙을 늘리면 안 되는가?**

```java
// 현재: -Xmx2G (문제 있음)
// 제안: -Xmx4G (근본 해결 안 됨)

이유:
1. Old Generation 시간 증가
   - Old Gen이 2배가 되면 Full GC할 때 순회 시간도 2배
   - GC Pause가 더 길어질 수 있음

2. 단편화 문제는 여전함
   - 힙 크기와 무관하게 할당/해제 패턴이 같으면
   - 단편화 정도는 유사

3. 메모리 비용 증가
   - 서버 리소스 낭비
   - 다른 프로세스를 위한 여유 감소
```

**올바른 접근:**

```java
// 1단계: 메모리 사용 패턴 개선
List<ResultEntity> results = new ArrayList<>();

for(int i = 0; i < 3_000_000; i++) {
    Data data = fetchData(i);
    ProcessedResult result = complexLogic(data);
    results.add(result);
    
    // 배치 사이즈만큼 모였을 때 한 번에 저장
    if(results.size() >= 10_000) {
        saveResults(results);  // DB에 저장
        results.clear();       // 메모리 해제
    }
}

// 2단계: 모니터링
// jstat -gcutil -h20 [pid] 1000
// Young Gen GC 시간: ~200ms 유지
// Full GC: 1-2회/배치 (불가피)

// 3단계: 힙 크기 최적화
// -Xmx1500M (Old Gen: ~750MB)
// Old Gen이 70-80% 찬 후에 Full GC 발생하도록 설정
```

### 핵심 개념 정리

- **Generational Hypothesis**: Young Gen에서 대부분 객체가 죽으므로, 영역을 나누어 효율적으로 관리
- **Memory Fragmentation**: 할당/해제 반복으로 인한 연속된 메모리 부족 상태
- **Full GC vs Minor GC**:
  - Minor GC: Young Gen만 (~100-300ms)
  - Full GC: Entire Heap (초 단위)
- **Survivor Space**: 객체의 수명 판정 영역 (age counter 사용)
- **Promotion Threshold**: Young → Old로 넘어가는 기준 (기본 15)

### 실무 포인트

| 상황 | 진단 방법 | 해결책 |
|------|---------|--------|
| GC Pause 증가 | `jstat -gc` 로그 분석 | 메모리 패턴 개선 우선 |
| Old Gen 빠르게 차음 | Heap Dump 분석 | 불필요한 객체 참조 제거 |
| Full GC 빈도 높음 | GC 로그 타임스탬프 | 배치 사이즈 조절 |

**모니터링 명령어:**
```bash
# 1. GC 로그 활성화
-Xlog:gc*:file=gc_%t.log:time,uptime,level,tags:filecount=5,filesize=100m

# 2. 실시간 모니터링
jstat -gc -h20 [pid] 1000
jstat -gcutil -h20 [pid] 1000

# 3. 분석 도구
java -jar gcloganalyzer.jar gc_2024*.log
```

## 질문 2: 월초 특정 시간대의 응답 시간 저하 원인

### 모범 답안

**현상의 메커니즘:**

이것은 **Concurrent Mark-Sweep(CMS) GC 또는 Serial GC의 'Stop-The-World' 현상**과 **Old Generation의 예측 불가능한 Full GC 발생**입니다.

```
평상시 (응답시간: 50ms)
Request → Young GC (Stop-The-World: ~50ms) → Response
        ↓
        대부분 객체가 Young Gen에서 소멸

월초 특정 시간대 (응답시간: 200ms+)
Request → Young GC (100ms) + Full GC (100-200ms) → Response
        ↓
        Old Generation이 갑자기 차서 Full GC 필요
```

**Young vs Old Generation 차이와의 연관:**

```java
// 메모리 구조 (예: -Xmx1G, -Xms1G)
Heap (1GB)
├─ Young Generation (300MB)
│  ├─ Eden (240MB)      ← 신규 객체 할당
│  ├─ Survivor 0 (30MB) ← 한 번 살아남은 객체
│  └─ Survivor 1 (30MB)
│
└─ Old Generation (700MB)
   ├─ 비워질 여유: ~200MB
   └─ 사용 중: ~500MB

시나리오 1: 평상시
┌─────────────┐
│ Request 1   │ → Young GC 발생 (200-300MB 정리) → OK
│ Request 2   │ → Young GC 발생 → OK
│ Request 3   │ → Young GC 발생 → OK
└─────────────┘
GC Pause: ~50ms × 3 = 150ms (응답 대기)

시나리오 2: 월초
┌─────────────┐
│ Request 1   │ → Young GC (100ms)
│ Request 2   │ → Young GC (100ms) 
│ Request 3   │ → Young GC (100ms)
│ ...이 반복되면서
│ Request
